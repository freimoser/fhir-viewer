FHIR-Condition-Beispiel: Diagnose als JSON lesen

Condition beschreibt laut Spezifikation eine klinische Bedingung, ein Problem oder eine Diagnose, die so relevant geworden ist, dass sie festgehalten wird. Das Beispiel ist eine aktive, bestätigte Verbrennung am linken Ohr. Codierungen aus SNOMED CT wurden entfernt; der Freitext in code.text trägt die Aussage.

Die Daten bleiben in Ihrem Browser: Es wird nichts hochgeladen. Nur zur Ansicht, kein Validator, kein Medizinprodukt.

Beispiel „Condition“: Original in der FHIR-Spezifikation R4, Lizenz CC0 1.0. Hier ohne SNOMED-CT-Codierungen und ohne Narrativ (text), weil SNOMED CT gesondert lizenziert ist.

Das Beispiel Feld für Feld

Die Tabelle zeigt die Elemente des Beispiels, wie sie in der hier verwendeten Fassung stehen:

ElementWert im BeispielBedeutung
clinicalStatus.coding[0].code"active"Klinischer Status, hier active. Der Wert stammt aus einer festen Liste (Bindung „required“).
verificationStatus.coding[0].code"confirmed"Wie sicher die Diagnose ist; die Spezifikation nennt unconfirmed, provisional, differential, confirmed, refuted und entered-in-error. Hier confirmed.
category[0].coding[0].code"encounter-diagnosis"Einordnung, hier encounter-diagnosis: eine Diagnose im Rahmen eines Kontakts (die Alternative ist ein Eintrag der Problemliste).
code.text"Burnt Ear"Freitext der Diagnose. Das Element code ist in R4 optional (0..1); im Beispiel steht hier nur Text.
bodySite[0].text"Left Ear"Körperstelle als Liste (0..*).
subject.reference"Patient/example"Pflichtfeld (1..1): Wer hat die Diagnose?
onsetDateTime"2012-05-24"Beginn (onset[x]): ein Datum, ein Datum mit Uhrzeit oder ein Alter.

Was die Spezifikation dazu sagt

Condition hat den Reifegrad „Trial Use“ (Maturity Level 3) und ist laut Spezifikation eine Event-Ressource im FHIR-Workflow. Sie kann eine Diagnose im Rahmen eines Kontakts sein, ein Eintrag der Problemliste oder ein Anliegen, das nicht auf der Problemliste steht. Zwei Regeln der Spezifikation betreffen die Statusfelder: clinicalStatus darf nicht vorkommen, wenn verificationStatus den Wert entered-in-error hat, und soll vorhanden sein, wenn die Kategorie problem-list-item ist und der Verifizierungsstatus nicht entered-in-error.

Im Viewer ausprobieren

Ändern Sie das Beispiel im Eingabefeld und klicken Sie auf „Anzeigen“. Beim Erzeugen dieser Seite wurden die folgenden Änderungen mit demselben Code geprüft:

  • Setzen Sie in verificationStatus den Code confirmed auf entered-in-error, lassen Sie clinicalStatus stehen. Der Viewer meldet: „clinicalStatus darf bei verificationStatus "entered-in-error" nicht vorkommen (Regel con-5).“ (Warnung)
  • Löschen Sie das Feld subject. Der Viewer meldet: „Pflichtfeld "subject" fehlt (in R4 mit Kardinalität 1..1).“ (Warnung)

Im FHIRPath-Tester liefert clinicalStatus.coding.code den Wert "active".
